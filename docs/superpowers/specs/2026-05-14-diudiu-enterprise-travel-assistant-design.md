# Diudiu Enterprise Travel Assistant 接入设计

## 1. 目标

- 在现有个人作品集站点中新增第三个代表项目：`Diudiu Enterprise Travel Assistant`
- 保持当前“代表项目”模块的整体设计语言、内容模型和详情页表达方式一致
- 不打乱当前首页第一屏已存在的两个代表项目排序
- 让新项目作为代表项目模块的下一页内容出现，并提供完整 case study 详情页

## 2. 设计结论

### 2.1 接入策略

- 保留当前第一页的两个代表项目不变
- 将 `Diudiu Enterprise Travel Assistant` 放入代表项目模块的下一页，而不是与前两个项目并列在同一屏
- 继续复用现有的内容驱动结构：
  - `ProjectSummary`
  - `CaseStudyContent`
  - 首页代表项目弹窗
  - 独立详情页路由

### 2.2 一致性原则

- 保持现有“首页项目摘要 -> 弹窗预览 -> 详情页 case study”的信息层级
- 保持现有代表项目模块的语气、密度和版式节奏
- 不直接嵌入 `travel-agent-guide` 独立项目的完整前端界面
- 仅提炼其产品定位、核心能力、架构判断、结果表达与项目 ownership，转译成当前站点统一的案例语言

### 2.3 命名策略

- 作品集中的正式标题使用：`Diudiu Enterprise Travel Assistant`
- slug 使用稳定、可读的英文路径
- 页面文案中允许补充中文定位，但标题本身不改写

## 3. 首页代表项目模块设计

### 3.1 保持现状

- 当前第一页继续展示现有两个代表项目
- 不改变这两个项目的顺序、文案重心和视觉优先级

### 3.2 新增第二页

- 代表项目模块新增下一页内容
- `Diudiu Enterprise Travel Assistant` 出现在这一页中
- 用户通过现有模块中的翻页按钮切换到该页
- 如果当前交互实现是左右切换，则沿用现有手感，只扩展数据与分页逻辑
- 如果当前交互实现本身已经带有“上一页 / 下一页”的概念，则不新增新的导航模式

### 3.3 首页项目卡表达

首页项目卡需要延续当前代表项目卡的表达方式，但突出这是一个偏产品原型的垂直 AI 助手案例。

建议卡片信息包括：

- 标题：`Diudiu Enterprise Travel Assistant`
- 类型：`Prototype Case` 或与现有分类兼容的展示标签
- 一句话定位：
  - 面向企业差旅场景的 production-style AI assistant，围绕制度问答、行程规划、合规提醒、票据解析与依据回溯构建完整工作流
- 核心证据：
  - `Policy Q&A / Itinerary Planning / Compliance Check / Ticket Parsing / Evidence Retrieval`
- 关键结果表达：
  - 不硬凑业务增长指标
  - 以“完成工作流闭环”“具备可演示前后端原型”“支持依据回溯”等更真实的原型结果表达为主

## 4. 详情页叙事结构

该项目虽然是原型，但在作品集中仍按完整 case study 处理，保持与其他代表项目一致的阅读体验。

### 4.1 Hero

- 项目标题：`Diudiu Enterprise Travel Assistant`
- 项目副标题：
  - 面向企业差旅场景的 production-style AI assistant，支持制度问答、行程规划、合规提醒、票据解析与依据回溯
- 项目概述：
  - 强调这不是“再做一个聊天框”，而是把差旅制度理解、出行建议、票据识别和依据返回组织成可演示、可扩展、可验证的产品工作流
- Meta 信息：
  - 角色
  - 时间
  - 案例类型
- Hero visual：
  - 使用与项目能力相匹配的 workflow 可视化
  - 节点建议为：
    - `Policy Q&A`
    - `Itinerary`
    - `Compliance`
    - `Ticket Parsing`
    - `Evidence`

### 4.2 Framing

回答“为什么企业差旅不是一个简单问答问题”。

内容重点：

- 制度规则分散在文档与流程中
- 员工对审批、酒店、补贴、票据的高频问题重复出现
- 单次回答不够，必须结合上下文形成后续行程建议
- 如果缺少依据返回与合规提示，用户难以信任结果

### 4.3 Product Judgement

核心判断需要明确写出：

- 这不是通用聊天产品，而是垂直工作流产品
- 关键不是“模型能不能答”，而是“能不能把制度理解、行程建议、票据解析和证据回溯串成一个闭环”
- 原型价值不在于堆技术名词，而在于验证该场景的产品边界与工作流可行性

### 4.4 System Design

详情页中应将系统设计拆成五个核心模块：

1. `Policy Q&A`
   - 基于制度文档回答差旅相关问题
2. `Itinerary Planning`
   - 根据出差意图和票据上下文生成落地行程建议
3. `Compliance Check`
   - 对预算、审批、补贴、报销相关风险进行提醒
4. `Ticket Parsing`
   - 从票据或截图中提取出发地、目的地、时间、交通方式等信息
5. `Evidence Retrieval`
   - 给回答附带匹配到的制度依据，提升可追溯性

### 4.5 Prototype Stack

为了区别于前两个项目，这个案例可以单独增加一个更轻量的原型架构区块，说明其工程组织方式。

建议内容：

- React + TypeScript 前端工作台
- FastAPI 后端接口
- 向量检索 / RAG 能力
- 票据解析链路
- 健康检查与基础服务状态

这里强调“原型可运行”和“结构清晰”，不写成大而全的平台架构图。

### 4.6 Outcome

结果表达以“产品原型完成度”和“闭环验证”为主。

建议结果方向：

- 完成从制度问答到依据回溯的闭环
- 完成从票据上传到行程补全的联动链路
- 前后端职责分层清晰，具备独立演示能力
- 工作台交互已具备产品化表达，不是单纯接口 demo
- 具备后续接入真实供应商 API、增强合规逻辑和扩展文档解析的演进空间

### 4.7 Ownership

重点突出以下 ownership：

- 场景定义与范围收敛
- 能力拆解与工作流编排
- 前后端原型组织思路
- 产品展示方式与体验表达
- 将独立项目整理为适合作品集讲述的案例结构

### 4.8 Reflection

建议沉淀为以下方向：

- 垂直 AI 助手的价值在于任务闭环，而不是更像聊天
- 依据返回与合规提示是企业场景可信度的关键
- 一个优秀的 prototype 不只是“能跑起来”，还要能清楚表达产品判断

- 允许为新项目定制独立 hero visual，但不能破坏整体审美连续性

## 7. 实施后验证标准

完成后应满足以下标准：

- 首页第一页仍只看到原有两个代表项目
- 用户可通过现有翻页入口切换到包含 `Diudiu Enterprise Travel Assistant` 的下一页
- 新项目在首页、弹窗、详情页三层信息里表达一致
- 新详情页的模块设计与前两个案例保持统一语言
- 路由可正常访问
- 测试与构建通过
- 本地服务可以正常启动用于预览

## 8. 约束与假设

- 假设当前作品集站点继续以案例表达为主，而不是变成项目仓库导航页
- 假设 `Diudiu Enterprise Travel Assistant` 在作品集中的最佳角色是“完整原型案例”，而不是“外链项目卡”
- 假设新增项目后，首页模块可以接受分页式承载第三个代表项目，而不要求同时并列展示三个卡片
